## 1. 一句话定义

> 给 DeepSeek Harness 的 Web 界面加一个「🔊 播放键」：**每条 AI 回答末尾的动作行**（复制 / 点赞 / 点踩所在的那排）里多出一个语音按钮，点一下就把这条回答读出来，再点一下停止。语音用你在百炼注册的音色合成，配置在「设置 → 语音」里完成。

**交互模型：完全由用户驱动（pull），而非模型驱动（push）。**

| 维度 | 参考项目（旧） | 本项目（v2.0） |
| --- | --- | --- |
| 谁决定"什么时候读" | 模型（系统提示注入指令） | **用户（点击播放键）** |
| 播放在哪里 | 输入框下方常驻语音条 | **消息末尾按钮原地播放** |
| 模型参与度 | 需要模型配合调工具（有概率忽视） | **零参与，100% 可靠** |
| 重复收听成本 | 每次重新合成 | **内容哈希缓存，免费** |
| 上下文开销 | 每轮注入系统提示 | **零** |

> 💡 这个重构顺带消灭了参考项目的已知缺陷——"有概率 AI 不回复（忽视提示）"，因为不再依赖模型配合。

### 2.2 messageId → 文本 的取回路径（P0 已实测定案）✅

播放键 slot 条目只拿到 `{ messageId }`（+ session 级 runtime props 含 `sessionId`）。**点按钮时要拿到这条回答的纯文本**，两条路径**都实现了**，先快后慢：

| 路径 | 实测结论 | 落地 |
| --- | --- | --- |
| **A. 客户端解析** | ✅ **可行且是主路径**。`dsh-client-ui-chat` 通过 `ctx.uiSession.provide({ hooks: ['chat'], resolve })` 声明了一个 session 级 hook，并在 `slots.d.ts` 里声明合并进 `SessionStandardProps`：**`useChat`**。任何 session scope 的 slot 条目因此都能拿到 `useChat`，从 `ChatSnapshot.legacy.nodes` 里按 `messageId` 找到 `AssistantMessageNode`，取 `blocks` 中 `kind==='text'` 的块拼起来 —— 与宿主"复制"按钮用的同一套规则。 | `client/shared.js` 的 `textOfMessage()` |
| **B. 宿主解析** | ✅ **兜底**。客户端给不出文本时（消息滑出已加载窗口）宿主按 messageId 扫 `$DSH_HOME/sessions` 下的会话日志；客户端给过的文本还会被 `remember()` 记住。 | `host/texts.js` |

> 两条路都落空才报"没找到这条回答的文本"，不会静默失败。**§2.2 的未知项已清除，不构成方案性风险。**

### 2.2b cordis 4 的插件配置传递方式（P0 实测）🔴 **与参考项目不同**

参考项目（0.1.0-rc.7）用 `ctx.settings.register(settingsNamespace(ns), schema)`；**0.2.1 上 `settingsNamespace` 已不存在**。实测：

- 插件配置改由 **`export const Config = z.object({...})`** 声明（cordis 的 Config）；
- 读取方式是 **`apply(ctx, config)` 的第二个参数**（`runtime.callback(this.ctx, this.config)`），**不是 `ctx.config`** —— 读 `ctx.config` 会抛 `cannot get property "config" without inject`；
- 设置页由 `ctx.settings.describe()` 从插件 Config schema 自动生成；要自定义页面就 `ctx.settings.configure({ auto: false }, owner)` 并挂 `settings.section` slot；
- 密钥脱敏仍然靠 `.role('secret')`（`dsh-settings` 的 redact walker 认这个 meta）；
- `Config` 必须在模块顶层**同步**求值，所以 `schemastery` 要用 `createRequire` 同步取（它有 `.cjs` 入口）。

## 3. v1 范围

### 3.1 做什么

| 模块 | 作用 |
| --- | --- |
| **消息播放键** | AI 回答末尾动作行中的 🔊 按钮：点击合成并播放该条回答；播放中变停止按钮；再次点击停止 |
| **合成引擎（Node）** | 直调 DashScope 非实时 TTS HTTP 接口，音频落盘 |
| **内容哈希缓存** | 相同内容+音色+模型的请求直接复用已合成音频，不重复计费 |
| **语音设置页** | 「设置 → 语音」：密钥 / 模型 / 音色 / 输出目录 / 开机音开关 + 保存 / 试听 / 打开文件夹 / 清理 |
| **开机提示音** | 页面首次交互时播放一次（沿用参考项目方案） |

### 3.2 明确不做（v1 范围外）

| 不做 | 原因 | 排期 |
| --- | --- | --- |
| **`voice_speak` 工具** | 播放完全由用户驱动；无系统提示注入后模型没有调用动机（决策 #8） | 永久移出 v1 |
| **系统提示注入** | 同上 | 永久移出 v1 |
| **语音条（composer.dock）** | 被"消息末尾播放键"取代 | 永久移出 v1 |
| **STT / 麦克风录音 / 双向语音对话** | 依赖浏览器录音 + paraformer 对接。注：0.2.1 已自带 `dsh-experimental-api-speech-to-text` 与实验性 voice-input 插件，v2 可考虑实现其 provider 接口接入百炼 paraformer | v2 |
| **声音复刻 / 声音设计管理界面** | v1 假设音色已在百炼控制台注册好 | 不做 |
| **本地 TTS 引擎** | 已拍板走云端 | 不做 |

### 3.3 交互细节（播放键）

```
状态机：idle 🔊 → (点击) → loading ⏳ → (就绪自动播) → playing ⏹ → (点击) → idle
                                    └→ (失败) → idle（按钮 title 显示错误原因）
```
- 按钮放在动作行 slot 列表中（复制与分支之间，`extraActions` 位置），视觉与现有图标按钮一致
- 播放使用浏览器 `<audio>`，播放完自动回到 idle
- **自动播放限制兜底**：点击本身就是用户手势，天然满足浏览器 autoplay 策略（比参考项目的语音条自动播更可靠）
- 长回答：全文合成，防御性截断到 API 上限 20000 字符
- Markdown 清洗：合成前去除 Markdown 标记符号，避免把 `**`、`#`、链接 URL 读出来

## 4. 技术方案

### 4.1 架构

```
┌─ Node 端（可信环境）───────────────────────────────┐
│  host/settings.js   cosyvoice 设置命名空间（apiKey 为 secret）│
│  host/speech.js     SpeechClient：直调 DashScope HTTP + 哈希缓存 │
│  host/store.js      AudioStore：音频落盘 / 按 hash 查找 / 清理    │
│  host/routes.js     /dsh-cosyvoice/{speak,audio,boot,open,clear} │
│  host/index.js      apply()：总装                              │
└──────────────────┬─────────────────────────────────┘
                   │ HTTP（同源，JSON + 音频字节）
┌──────────────────▼─────────────────────────────────┐
│ 浏览器端（Cordis 沙箱 iframe，纯拼接产物 lib/client.js）│
│  client/message-button.js  assistant-actions slot 播放键 │
│  client/settings-page.js   「设置 → 语音」页              │
│  client/boot-sound.js      开机提示音                     │
└─────────────────────────────────────────────────────┘
```

### 4.2 合成链路

```
POST /api/v1/services/audio/tts/SpeechSynthesizer   （非流式）
Headers: Authorization: Bearer <apiKey>
Body: { "model": "cosyvoice-v3.5-plus",
        "input": { "text": "<清洗后的文本>", "voice": "<voiceId>",
                   "format": "mp3", "sample_rate": 24000 } }
→ 200 { output: { audio: { url | data, expires_at } }, usage: { characters } }
→ Node 下载音频字节 → 落盘 → 返回 { name, url, cached }
```

**错误码映射**（写入 `speech.js`）：

| 状态码 | 含义 | 用户提示 |
| --- | --- | --- |
| 401 | Key 无效 | "API Key 无效，请在设置中检查" |
| 418 | 模型与音色不匹配 | "合成模型与注册音色时的模型不一致" |
| 4xx 其他 | 参数问题 | 原样转述 message |
| 5xx/网络 | 服务/网络故障 | "百炼服务暂不可用，稍后重试" |

### 4.3 关键技术决策

| 决策 | 选择 | 理由 |
| --- | --- | --- |
| 挂载点 | **`conversation.chat.assistant-actions` slot** | 0.2.1 官方扩展点（点赞/点踩同款），`kind:'list'` 天然支持多按钮 |
| 合成引擎 | Node 直调 DashScope HTTP | 零 Python 依赖；可注入 fetch 可测试 |
| 通信方式 | HTTP 路由（非类型化 RPC） | 参考项目已验证；送 JSON + 音频字节无需 wire schema |
| 浏览器端构建 | 纯拼接（`build.mjs`） | 参考项目已验证；天然满足单文件/无动态 import/不引 Node 内置模块三大硬约束 |
| 音频存储 | 插件自管目录（`$DSH_HOME/voice/audio`），文件名 = 内容哈希 | 支撑缓存；插件无 session，自管目录最稳 |
| 密钥处理 | schemastery `role('secret')` | 永不回传浏览器 |
| 命名隔离 | 设置命名空间 `cosyvoice`、路由前缀 `/dsh-cosyvoice` | 与参考项目可共存于同一 dsh |

### 4.4 内容哈希缓存

```
cacheKey = sha256( model + '\n' + voiceId + '\n' + 清洗后文本 )
文件名 = <cacheKey>.mp3
```
- 命中：直接返回已有文件 URL（`cached: true`），**零 API 费用**
- 未命中：合成 → 落盘 → 返回
- 收益：重复收听、多设备看同一会话、设置页反复试听，均不再计费
- 「清理文件」按钮清空该目录即全量失效

## 5. 配置项设计

**设置持久化**：`$DSH_HOME/settings.yaml` 的 `cosyvoice:` 段，可直接手工编辑，运行中热读取。

| 字段 | 类型 | 默认 | 说明 |

密钥（密码框，留空=不修改，显示已配置/未配置）· 模型 · 音色 ID · 输出目录覆盖 · 开机音开关 · 保存 / 试听 / 刷新 / 打开文件夹 / 清理文件。

### 10.2 V2-1：修复加载图标"整体旋转"

| 项 | 内容 |
| --- | --- |
| 现象 | 合成中转圈图标除了弧在转，**整个图标也在转**，不美观 |
| 根因 | `client/message-button.js` 的 `IconBusy()` 里，`<animateTransform>` 是 `<svg>` 的**直接子元素**。按 SVG 规范，动画元素作用于其**父元素**，因此它旋转的是**整个 `<svg>` 根**（连带弧一起绕 `(12,12)` 转），弧本身并未相对旋转 |
| 修复 | 用 `<g>` 包裹弧，把 `animateTransform` 放进 `<g>` 内，使旋转只作用于弧；`<svg>` 根不再受任何 transform 影响 |
| 影响面 | 仅 `client/message-button.js` 一处，约 3 行 |
| 验收 | 合成中：弧绕图标几何中心匀速旋转，图标整体在按钮内**无位移、无摆动**；与宿主其他动作按钮（复制/点赞）视觉重量一致 |

### 10.3 V2-2：音色档案（Voice Profiles）

**需求**：现在只能配一种音色。需要能保存多套音色档案，每套自定义**名称 / 音色 ID / 使用模型**，并在列表间切换。

**数据结构**（`~/.dsh/voice/profiles.json`）：

```json
{
  "version": 1,
  "activeId": "p_a1b2",
  "profiles": [
    {
      "id": "p_a1b2",
      "name": "我的声音",
      "voiceId": "cosyvoice-v3.5-plus-myvoice-xxxx",
      "model": "cosyvoice-v3.5-plus",
      "source": "clone",
      "status": "ready",
      "createdAt": "2026-10-07T11:40:00+08:00"
    }
  ]
}
```

| 字段 | 说明 |
| --- | --- |
| `source` | `clone`（本插件克隆）/ `manual`（手填 ID）/ `cloud`（从云端列表同步） |
| `status` | `ready` / `pending`（克隆中，待就绪）/ `failed` |

**存储为什么自管而不进 dsh 配置 schema**：

- schemastery 的**数组/嵌套对象**通过 `ConfigForms` 做「按路径增量写入」时行为不可靠，复合结构易踩坑；
- 设置页本就是**自绘 UI**（`settings.section` slot），自管 JSON 不受 schema 渲染限制；
- 克隆音色时需要**直接落盘**并带 `status` 状态机，自管更直接。

**配置 schema 变更**：保留 `apiKey`、`outputDir`、`bootSound`；`model` / `voiceId` 降级为**无档案时的回退值**（兼容 v1 已有配置）。激活档案以 `profiles.json` 的 `activeId` 为准。

**设置页 UI**：档案列表（名称 + 模型 + 状态徽标）→ 选中即切换；支持**新增**（手填名称/音色ID/模型）、**编辑**、**删除**、**设为当前**；顶部提供「从云端同步」与「克隆新音色」入口。

**验收**：新增 3 套档案并来回切换，每次试听用的是当前档案的 `voiceId`+`model`；重启 dsh 后档案与激活项保持；v1 老配置（只有 `voiceId`）仍能正常合成。

### 10.4 V2-3：音色克隆（上传音频 → 自动获得音色 ID）

**需求**：不想再手工准备音色 ID。希望**上传一段音频，插件自动完成复刻并返回音色 ID**。

**关键结论（已调研确认）**：百炼提供官方 **Files 上传接口**，因此**不需要用户自己配 OSS**，插件可完全闭环。

**完整链路**：

| 步 | 调用 | 说明 |
| --- | --- | --- |
| ① | `POST https://dashscope.aliyuncs.com/api/v1/files`<br>`multipart/form-data`：`files=@音频`、`purpose=voice_clone`、`descriptions`（可选） | 上传音频，返回 `data.uploaded_files[0].file_id` |
| ② | `GET https://dashscope.aliyuncs.com/api/v1/files/{file_id}` | 取 `data.url` —— **阿里云内网可访问的临时签名 URL** |
| ③ | `POST https://dashscope.aliyuncs.com/api/v1/services/audio/tts/customization`<br>`{model:"voice-enrollment", input:{action:"create_voice", target_model, prefix, url, language_hints:["zh"]}}` | 返回 `output.voice_id`，格式 `{target_model}-{prefix}-{唯一标识}` |
| ④ | 同端点 `action:"query_voice"` 轮询 | `status`：`DEPLOYING` → `OK`（就绪，可合成）；`UNDEPLOYED`（失败） |
| ⑤ | 写入 `profiles.json` | `source=clone`，成功后 `status=ready` |

> **② 是必须的**：`create_voice` 的 `url` 只接受**阿里云内网可访问**的地址，直接用外部公网直链会报 `AudioSilentError`。这正是要走 Files 接口的原因。

**同步云端音色列表**：同端点 `action:"list_voice"` 返回 `output.voice_list`，把用户此前在百炼控制台创建的音色一键拉进档案（`source=cloud`），彻底告别手填 ID。

**音频与配额约束**：

| 约束 | 值 |
| --- | --- |
| 音频建议 | **WAV、48kHz、10~20 秒**；可设 `max_prompt_audio_length` `[3.0, 30.0]`（默认 10）、`enable_preprocess`（降噪/增强，安静环境建议关） |
| `prefix` | 仅**数字与小写字母**，≤ 10 字符 |
| `target_model` | 必须与后续合成所用模型一致，否则合成失败 |
| 音色配额 | **30 个 / 账号**（满了需先删除不用的） |
| Files 配额 | 单文件 ≤ 1GB，总量 5GB，文件数 100 |
| 就绪耗时 | 通常几秒到几分钟，必须轮询 |

**UI 与状态机**：上传 → `pending`（"复刻中"，可轮询查看）→ `ready`（可用，自动入档案并可试听）/ `failed`（展示失败原因）。

**两处实现取舍**：

- **上传用裸音频字节而不是 multipart**：两端都是本插件自己写的，走 `content-type: application/octet-stream` + 查询串带文件名，就不需要引入 multipart 解析器；单文件上限 20MB，超过给 413。
- **轮询放在客户端**：`POST /clone` 只做完 ①②③ 就返回一条 `pending` 档案（此刻用户就该在列表里看见它），浏览器每 3 秒问一次 `/clone/status`，两分钟超时不判失败。服务端不挂长请求，页面关掉也不会留下 orphan 轮询。
- **就绪即自动设为当前音色**：用户上传一段音频，默认就是想用它；想换回去点一下即可。

**验收**：上传一段 15 秒 WAV → 自动得到音色 ID → 档案出现在列表且状态 `ready` → 用它试听成功；"从云端同步"能拉到控制台既有音色；音色创建失败时给出可读错误（音频质量问题 / 配额已满 / 模型不匹配）。

### 10.5 V2-4：分句并行合成 + 按句依次播放

**现状问题**：整段文本一次性上传合成，字数越多耗时越久，点击后要等很久才出声。

**对用户原方案（分句上传再拼接）的评估**：方向正确，但**"拼接"这一步不建议做**：

| 问题 | 说明 |
| --- | --- |
| 韵律断裂 | 每句独立合成，句间停顿与语调衔接不如整段自然；过短的句子还可能因缺上下文而质量下降 |
| 拼接风险 | mp3 直接字节拼接多数播放器能响，但可能**爆音**、**时长元数据不准** |

**采纳方案：按句并行 + 按序依次播放（不拼接）**

1. **切句**：按句末标点（`。！？；…` / `.!?`）、换行切分；单句上限约 120 字（超限再按逗号细分）；过短句（< 8 字）与相邻句合并，避免切碎。
2. **并行合成**：并发限流约 3（可配），避免触发 QPS 限制。
3. **首句优先**：第一句合成完成即返回并**立刻开始播放**，后续句子后台并行产出、按序排队。
4. **按序播放**：浏览器维护播放队列，`ended` 事件触发下一句，并**预加载下一句**以压缩句间间隙。全程不做字节拼接。
5. **句子级缓存**：缓存键变为 `sha256(model + voiceId + 句文本 + 参数)`。重复句子直接命中，越用越快、越省；同时保留整段文本 → 句子清单的映射缓存。

**可用的 API 参数（已确认）**：TTS 支持 `format`（`mp3` 默认 / `pcm` / `wav` / `opus`）、`sample_rate`（8000/12000/16000/22050/24000/44100/48000）、`rate`、`pitch`、`volume`。本方案默认沿用 `mp3`；若将来要做导出，改用 `wav`/`pcm` 即可可靠拼接（只需重写 header）。

**未采纳 / 备选（记录在案）**：

| 方案 | 评价 |
| --- | --- |
| 全部合成完再拼接成单个文件 | ❌ 不采纳（韵律 + 拼接风险；且本版不需要导出） |
| **API 原生 SSE 流式**（`X-DashScope-SSE: enable`） | ⭐ 备选。服务端自行分句、按句推音频块，韵律最完整、首包最快；但宿主要做 SSE 代理 + 浏览器流式播放，复杂度明显更高。留作后续优化 |
| 导出/下载完整音频 | ❌ 本版不做（用户已确认只求播放快） |

**验收**：一段约 800 字的回答，点击后**首句出声时间**较 v1 显著下降（目标 < 2s）；播放过程中句间无明显卡顿；同一段第二次点击因句子级缓存近乎瞬时；并发限流生效、不触发限流报错。
